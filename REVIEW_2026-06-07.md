# Project Review: pb138

**Date:** 2026-06-07

---

## Project Orientation

The project is a Turborepo monorepo with two apps: `apps/server` (Elysia + Drizzle ORM + PostgreSQL 17) and `apps/web` (React 19 + React Router DOM v7 + TailwindCSS v4 + shadcn/ui built on Base UI). The runtime is Bun throughout. Infrastructure is Docker-composed (Postgres, Redis, MinIO for image storage, Mailtrap for email). Auth is handled with `@elysiajs/jwt` and `Bun.password` (argon2) — a custom but well-structured implementation. The database enforces Row-Level Security policies via a dedicated `app_user` role and session GUCs. Packages are shared via a `packages/shared` workspace. The project is well-documented with `README.md`, API contract in `docs/API.md`, ERD in `docs/erd.dbml`, and functional requirements in `docs/FUNCTIONAL_REQUIREMENTS.md`.

## Detailed Review

### 1. Component Library

**Status:** ✅ Good

The project uses shadcn/ui built on top of Base UI (`@base-ui/react`) — a modern, accessible headless component approach. The `/apps/web/src/components/ui/` directory contains custom-wrapped variants for `button`, `input`, `select`, `textarea`, `card`, `dialog`, `badge`, `table`, `toast`, and `toaster`, all importing from `@base-ui/react/*`. These components are used consistently throughout the codebase.

A small number of raw HTML interactive elements are used outside the component library:
- `apps/web/src/components/RichTextEditor.tsx:204` — raw `<input type="file" ...>` for image upload (acceptable; file inputs are often not wrapped)
- `apps/web/src/pages/profile/ProfileInfoCard.tsx:158` — raw `<input type="file" ...>` for avatar upload (same pattern)
- `apps/web/src/pages/ArticleEditorPage.tsx:171` — raw `<input type="file" ...>` for cover image upload

All three are file-picker inputs, which are notoriously difficult to style via a component library and are acceptable as raw elements. No raw `<button>`, `<select>`, or `<textarea>` bypasses were found outside the library.

**Recommendations:**

1. The file input pattern is repeated three times. Consider extracting a shared `<FileInput>` component to ensure consistent behavior (validation, accessible label, styling) across all upload points.
2. Consider adding `lucide-react` or `@phosphor-icons/react` icons consistently — both are in dependencies but usage may be inconsistent. Audit icon library usage to standardize on one.

### 2. Styling

**Status:** ⚠️ Concerns

The project uses Tailwind CSS v4 with a theme-token approach. Most styling is clean and token-based. However, several issues exist:

**Arbitrary hex colors** — `apps/web/src/pages/ArticleEditorPage.tsx:492` and `:566` contain hardcoded hex arbitrary values:
```tsx
<div className="rounded-lg border border-[#dc2626]/20 bg-[#dc262608] px-5 py-4">
```
The color `#dc2626` is the standard Tailwind red-600, which maps to the `destructive` design token. These should be `border-destructive/20 bg-destructive/5`.

**Arbitrary tracking values** — Multiple pages use pixel-based tracking arbitrary values instead of theme tokens:
- `apps/web/src/pages/ArticlePage.tsx:42,43,313,317` — `tracking-[-0.3px]`, `tracking-[-0.5px]`, `tracking-[0.5px]`
- `apps/web/src/pages/SearchResultsPage.tsx:70` — `tracking-[-0.5px]`
- `apps/web/src/pages/CategoryPage.tsx:84,131` — `tracking-[-1px]`, `tracking-[-0.5px]`

**Inline `style={}`** — Used appropriately only for dynamic percentage-based bar widths that cannot be expressed as static Tailwind classes:
- `apps/web/src/components/stats/GlobalStatsDashboard.tsx:52`, `Timeline.tsx:25`, `HorizBar.tsx:15`, `NewspaperStatsDashboard.tsx:79`
- `apps/web/src/pages/ArticlePage.tsx:358` — `style={{ height: 1 }}` for an intersection observer sentinel

These dynamic uses are acceptable; no presentational `style={}` was found.

**`!important`** — `apps/web/src/index.css:35` uses `animation: none !important` for the `prefers-reduced-motion` media query. This is documented in a comment as intentional to override Lexical animations (`apps/server` commit message references this). Acceptable.

**One remaining arbitrary value** — `apps/web/src/components/stats/HorizBar.tsx:20` uses `ml-[9.75rem]` which is a magic-number offset for alignment. This is a smell that suggests a layout approach (flexbox/grid) might be cleaner.

**Recommendations:**

1. Replace `border-[#dc2626]/20 bg-[#dc262608]` in `ArticleEditorPage.tsx:492,566` with `border-destructive/20 bg-destructive/5` to use the design system token.
2. Define named theme tokens for the repeated tracking values (e.g., `--tracking-tight-headline: -0.5px`) in `index.css` and use them via Tailwind config, or accept a small set of documented arbitrary values in a comment.
3. Replace `ml-[9.75rem]` in `HorizBar.tsx:20` with a layout-based approach (e.g., a grid with a fixed column width) to avoid the magic number.

### 3. Loading Data

**Status:** ⚠️ Concerns

TanStack Query (`@tanstack/react-query`) is present and correctly configured with a `QueryClient` in `apps/web/src/lib/queryClient.ts` and wrapped at the app root in `apps/web/src/frontend.tsx`. Read queries (`useQuery`) are used correctly with stable array keys:

```ts
// apps/web/src/hooks/useNewspaper.ts
queryKey: ["newspaper", newspaperName],

// apps/web/src/pages/dashboard/EditorialQueueSection.tsx
queryKey: ["editorial-queue", newspaperId, currentPage],
```

Mutations are used with `useMutation` and proper `onError` / `onSuccess` invalidation in `EditorialQueueSection.tsx`.

However, a significant portion of data mutations bypass TanStack Query entirely, using raw `fetch()` calls directly inside component event handlers:

- `apps/web/src/pages/LoginPage.tsx:28` — login is a raw fetch
- `apps/web/src/pages/SignUpPage.tsx:39` — registration is a raw fetch
- `apps/web/src/pages/profile/ProfileInfoCard.tsx:57` — profile save is a raw fetch
- `apps/web/src/pages/profile/PasswordCard.tsx:30` — password change is a raw fetch
- `apps/web/src/pages/dashboard/ReviewQueueSection.tsx:42,68` — fetch review actions
- `apps/web/src/pages/director/ApprovalQueue.tsx:26,45` — director approval actions
- `apps/web/src/pages/director/BrandingSection.tsx:30` — newspaper branding update
- `apps/web/src/pages/director/PublicationQueue.tsx:21,41` — publication queue actions
- `apps/web/src/pages/admin/NewspaperUsersSection.tsx:51,71,107` — admin role management
- `apps/web/src/pages/dashboard/MyArticlesSection.tsx:43` — article delete action
- `apps/web/src/components/Navbar.tsx:116` — logout

This means these operations do not benefit from TanStack Query's loading/error state management, automatic cache invalidation, or optimistic updates. Each component implements its own ad-hoc loading/error state via `useState`.

**Recommendations:**

1. Migrate mutation-heavy components (`ReviewQueueSection`, `ApprovalQueue`, `BrandingSection`, `NewspaperUsersSection`) to use `useMutation` with `onError` toasts and `onSuccess` query invalidation — the same pattern already used in `EditorialQueueSection.tsx`.
2. Consider extracting a custom hook (e.g., `useLogin`, `useRegister`) to encapsulate the auth mutation logic and separate it from form/UI state.
3. Auth flows (login/signup) can reasonably remain as raw fetch calls since they trigger full navigation — but they should at minimum invalidate all queries on success.

### 5. REST API Design

**Status:** ✅ Good

Routes are resource-oriented with plural noun paths: `/api/newspapers/:newspaper_id/articles`, `/api/newspapers/:newspaper_id/categories`, `/api/newspapers/:newspaper_id/comments`, etc. No verb-in-path antipatterns were found for CRUD operations.

HTTP verbs are correctly applied: `GET` for reads, `POST` for creates, `PATCH` for partial updates, `DELETE` for removal. Status codes are semantically correct:
- `set.status = 201` on POST creates (`apps/server/src/routes/articles.ts:81`, images upload)
- `set.status = 204` on DELETE (`apps/server/src/routes/articles.ts:96`)
- `HttpError` with appropriate 400/403/404/409 codes used in services

Workflow action endpoints (`/submit`, `/review`, `/approve`, `/schedule`, `/publish`, `/assign-editor`) all use `POST` on sub-resources — the accepted REST convention for state machine transitions on a resource.

Request validation uses TypeBox schemas (via `drizzle-typebox`) defined in `apps/server/src/schemas/` with a file per domain (articles.ts, auth.ts, categories.ts, etc.). All route handlers wire `body`, `params`, and `query` schemas.

PATCH is used correctly for partial updates (`updateArticleBody` accepts optional fields, `/subscriber-only` changes a single flag).

**Recommendations:**

1. The `/api` root endpoint (`apps/server/src/server.ts:77`) performs a live database query and returns newspaper data mixed with a diagnostic message. This should be a simple health/meta endpoint returning only static info — move the newspaper list to `/api/newspapers`.
2. Consider adding a `429 Too Many Requests` response for the auth endpoints (login, register) to hint at future rate limiting — even if not implemented yet, it aligns with the contract.

### 6. Database

**Status:** ✅ Good

The schema (`apps/server/src/db/schema.ts`) is well-structured with proper relational design:
- UUIDs as primary keys throughout (`uuid().primaryKey().defaultRandom()`)
- Foreign keys with appropriate `onDelete: "cascade"` where child data should be removed with the parent
- Unique constraints: `email_newspaper_idx` on `(email, newspaper_id)`, `newspaper_slug_idx`, `article_category_slug_newspaper_unique`
- Compound primary keys for junction tables: `likes(userId, articleId)`, `userRoles(userId, newspaperId, role)`
- Enum types for `articleStateEnum`, `userRolesEnum`, `auditResultEnum`, `reviewDecisionsEnum`

No `bytea`/`blob` columns exist — images are stored externally in MinIO with only the URL persisted (e.g., `articleImages.url: text("url").notNull()`).

Six versioned SQL migration files exist in `apps/server/drizzle/` (0001 through 0006) plus one TypeScript migration (`addGlobalEmailUniqueIndex.ts`) — migrations are properly managed.

Drizzle ORM is used for all application queries. Raw SQL (`sql\`...\``) appears only in `apps/server/src/db/rls.ts` for the `SET CONFIG` GUC session parameters (which cannot be expressed via ORM) and in migration setup scripts — both acceptable.

**Recommendations:**

1. `articles.categoryId` is nullable (no `.notNull()`) but no FK action is set. If a category is deleted, the article's `category_id` becomes `null` silently. Consider adding an explicit `onDelete: "set null"` annotation to make the intent clear, or enforce non-null categories at the application layer.
2. The `globalRoles` table has `unique("global_roles_role_unique").on(table.role)` which limits each role to a single user globally. Verify this is the intended semantics for `SYSTEM_ADMINISTRATOR` and `DIRECTOR`.

### 7. BE Design Patterns

**Status:** ✅ Good

The server follows a clear two-layer architecture: **routes** (thin — wire params/body schemas, call service) → **services** (business logic + DB access). All DB calls live in `apps/server/src/services/` with no business logic leaking into route handlers.

Route files are minimal — each route handler is typically one line delegating to a service:
```ts
// apps/server/src/routes/categories.ts
.get("/api/newspapers/:newspaper_id/categories", ({ params, withDb }) =>
    withDb((tx) => categoryService.listCategories(tx, params.newspaper_id)),
```

Services contain role/authorization checks, domain validation, DB queries, and audit logging. The `withDb` pattern passes a transaction context cleanly.

There is no separate repository layer, but at this project scale, services fulfilling the repository role is appropriate and avoids unnecessary abstraction.

One minor issue: `apps/server/src/server.ts:78-91` contains a direct `db.select().from(newspapers)` call in the route handler body (the `/api` diagnostic endpoint), bypassing the service layer.

**Recommendations:**

1. Move the DB call in `server.ts:78-91` to a service function or simply return static metadata, to maintain the pattern consistently.
2. `apps/server/src/services/articles.ts` is likely a large file given the number of article operations (CRUD + submit + review + approve + schedule + publish + images). Consider splitting it into `articles.service.ts` and `article-workflow.service.ts` to keep files under 400 lines.

### 8. Auth

**Status:** ✅ Good

Authentication uses `@elysiajs/jwt` for JWT signing/verification — not raw `jsonwebtoken`. Passwords are hashed with `Bun.password` (argon2id) — not raw `bcrypt`. No known auth framework (BetterAuth, Lucia, etc.) is present, but the custom implementation is well-structured with:

- Email verification flow with time-limited JWT tokens
- Password reset flow with dedicated tokens
- 2-hour session token expiry (`apps/server/src/utils/jwt.ts:2`)

Authorization is enforced at two levels:
1. **Application level** — services check roles before performing operations (e.g., `apps/server/src/services/categories.ts:81` — `logger.warn("Category create failed: forbidden")` with 403; `apps/server/src/services/comments.ts:92` — checks `comment.userId === user.id` for ownership)
2. **Database level** — Row-Level Security policies set via `apps/server/src/db/rls.ts` using session GUCs `app.user_id`, `app.newspaper_id`, `app.roles`

The RLS approach provides defense-in-depth authorization that can't be bypassed by application bugs.

**Recommendations:**

1. Ensure all sensitive routes explicitly check the `authMiddleware` is applied. A route accidentally added without `.use(authMiddleware)` would expose data unprotected — consider a middleware-at-app-level approach or an audit of each route group.
2. The `JWT_SECRET=newspaper` in `.env.example` is obviously a placeholder — add a comment noting that production secrets must be cryptographically random (e.g., `openssl rand -base64 32`).

### 10. Logging & Monitoring

**Status:** ✅ Good

A custom structured logger (`apps/server/src/utils/logger.ts`) outputs NDJSON to stdout with `level`, `timestamp`, `message`, and arbitrary metadata. Supports `LOG_LEVEL` environment variable for filtering, optional `LOG_FILE` for file mirroring, and routes `error`/`warn` to `console.error`, `info`/`debug` to `console.log`.

The logger is consistently imported and used across all services:
```ts
logger.warn("Category create failed: forbidden", { userId: user.id, roles });
logger.info("Category created", { categoryId: created!.id, name, newspaperId });
logger.error("Unhandled server error", { method, url, status, error, stack });
```

The 48 `console.log` calls found are exclusively in `apps/server/scripts/` (db-setup, bootstrap-migrations, subscription-renewal) and `apps/server/src/db/seeds/` — none in the production application code paths. No sensitive values (passwords, tokens) were found in log calls.

**Recommendations:**

1. The custom logger re-implements what `pino` provides (structured JSON, level filtering, file transport). For a production system, replacing it with `pino` + `pino-http` would add request-per-line access logs, better performance, and ecosystem tooling. For a university project, the current custom logger is entirely sufficient.
2. The `subscription-renewal.ts` script uses `console.log`/`console.error` instead of the structured logger. Migrate to `logger.*` for consistency.

### 11. Error Handling

**Status:** ⚠️ Concerns

**Backend — Good:** A global `onError` handler in `apps/server/src/server.ts:94` catches all `HttpError` instances and returns the appropriate status code with a JSON body. Unhandled errors fall through to a 500 with structured logging. The `HttpError` class is used consistently across services for typed error responses.

**Frontend — Inconsistent:** Components using TanStack Query mutations (e.g., `EditorialQueueSection.tsx`) correctly use `onError` callbacks with toast notifications:
```ts
onError: () => toast({ title: "Error", description: "Failed to assign editor...", variant: "error" }),
```

However, components using raw `fetch()` calls have ad-hoc error handling with varying quality:
- `apps/web/src/pages/dashboard/ReviewQueueSection.tsx:42-65` — catches errors but has no user-visible error state for fetch failures
- `apps/web/src/components/StatisticsSection.tsx:47` — sets error state correctly: `.catch(() => { if (!cancelled) setError("Failed to load statistics."); })`
- `apps/web/src/pages/director/PublicationQueue.tsx` and `ApprovalQueue.tsx` — no evident error state rendering after fetch

**Recommendations:**

1. Standardize mutation error handling by migrating raw `fetch` calls to `useMutation` — this would consolidate error handling in one pattern (see Loading Data category).
2. Audit `ReviewQueueSection.tsx` and the director queue pages to ensure all mutation failures surface a user-visible message rather than silently failing.
3. Add React `ErrorBoundary` at the route level (not just for Lexical) to catch unexpected rendering errors in any page.

### 12. Security

**Status:** ✅ Good

**CORS:** Explicitly configured in `apps/server/src/server.ts:36-43` to allow only `process.env.FRONTEND_URL` (defaulting to `http://localhost:5173`). Not wildcard. Methods and headers are explicitly listed.

**Secrets in repo:** No API keys, tokens, or passwords found hardcoded in source. `.gitignore` covers `.env*` patterns.

**SQL injection:** All queries go through Drizzle ORM's parameterized query builder. The only raw SQL template literals (`sql\`...\``) are in migration scripts and `rls.ts` for `SET CONFIG` — none involve user-supplied values concatenated into SQL strings.

**Image handling:** Files are validated before upload (`blob.type` must be `image/jpeg` or `image/png`, size limits enforced), then processed through `sharp` and stored in MinIO. No blobs stored in the database.

**RLS:** Row-Level Security at the database level provides defense-in-depth — even if the application layer authorization is bypassed, the DB enforces visibility rules.

**Recommendations:**

1. The `JWT_SECRET` default in server startup is not validated for minimum entropy. Consider adding a check that `JWT_SECRET.length >= 32` and warning if not met.
2. Rate limiting is absent on auth endpoints (`/register`, `/login`, `/forgot-password`). For a production system this would be a significant concern; for the academic context, a comment noting this as a known gap would be appropriate.

### 13. Forms

**Status:** ❌ Issues

No form library (React Hook Form, TanStack Form, Formik) is present in `apps/web/package.json`. No form validation library (`@hookform/resolvers`, `yup`) is wired to the frontend.

The codebase implements forms via the **form-as-useState antipattern** — multiple `useState` hooks for each field, manual onChange handlers, and manual validation logic:

`apps/web/src/pages/SignUpPage.tsx` — 8 useState hooks for form state:
```tsx
const [fullName, setFullName]         = useState("");
const [username, setUsername]         = useState("");
const [email, setEmail]               = useState("");
const [password, setPassword]         = useState("");
const [confirmPassword, setConfirmPassword] = useState("");
const [error, setError]               = useState<string | null>(null);
const [fieldErrors, setFieldErrors]   = useState<Record<string, string>>({});
const [loading, setLoading]           = useState(false);
```
With a manual `if (password !== confirmPassword)` validation check before submit.

`apps/web/src/pages/profile/ProfileInfoCard.tsx` — 12 useState hooks including individual field states for `fullName`, `username`, `bio`, `profilePictureUrl`, `loading`, `error`, `success`, etc.

`apps/web/src/pages/profile/PasswordCard.tsx` — 7 useState hooks for `currentPassword`, `newPassword`, `confirmNewPassword`, `loading`, `error`, `success`.

`apps/web/src/pages/LoginPage.tsx`, `GlobalLoginPage.tsx`, `PasswordResetPage.tsx`, `SetNewPasswordPage.tsx` — all follow the same pattern.

This approach leads to duplicated state management logic, no declarative validation schema, and inconsistent field-level error display.

Zod is present as a root dependency (`"zod": "^3.25.0"` in root `package.json`) but is only used on the backend for schema validation, not the frontend.

**Recommendations:**

1. Adopt React Hook Form (`react-hook-form`) with Zod resolver (`@hookform/resolvers/zod`) for all forms. Start with the highest-complexity form (`ProfileInfoCard.tsx`) and work down.
2. Share Zod schemas between frontend and backend via the `packages/shared` workspace — the backend already has TypeBox schemas; the frontend form schemas can be Zod equivalents of the same shapes.
3. The `<FormField>` component (`apps/web/src/components/FormField.tsx`) is a good abstraction point — update it to accept `react-hook-form` `register` and `errors` props so it integrates cleanly with the library.
4. At minimum, consolidate the repeated `[loading, setLoading]` and `[error, setError]` useState pairs into a custom `useFormSubmit(fn)` hook that wraps async submission with loading/error state.

### 14. Frontend Structure

**Status:** ⚠️ Concerns

**God components:** Two page files significantly exceed the recommended ~300 line guideline for route-level components:

- `apps/web/src/pages/ArticleEditorPage.tsx` — **573 lines**. Mixes: multiple `useState` for form fields, cover image upload state, article metadata, rich text editor state, image gallery management, category/newspaper context, submit/save logic with raw fetch calls, and the full rendering of the editor UI. This is a significant god component that would benefit from decomposition.

- `apps/web/src/pages/ArticlePage.tsx` — **438 lines**. Contains: article data fetching, comment list with pagination, like/unlike mutations, comment submission, article view tracking, Lexical reader configuration, and full rendering. While the line count partly reflects rich JSX markup, the mixing of multiple concerns (viewing, commenting, liking) is notable.

**Custom hooks — too few:** Only 4 custom hooks exist:
- `useArticleViewTracker.ts` — intersection observer for view tracking
- `useCategory.ts` — query wrapper for category fetch
- `useNewspaper.ts` — query wrapper for newspaper fetch
- `useTheme.ts` — newspaper primary color theming

The large page files above contain logic that should be in custom hooks. For example, `ArticleEditorPage.tsx`'s image upload logic, auto-save logic, and article metadata management could each be a separate hook.

**Raw fetch in component bodies:** Multiple components place async `fetch()` calls directly inside event handlers (see Loading Data section). These belong in `useMutation` hooks or custom hooks.

**Router loaders:** The project uses React Router DOM v7 which supports `loader` functions. Critical data fetches in page components (e.g., article data in `ArticlePage.tsx`) could move to route loaders to enable parallel data loading. Currently all data fetching happens after the component mounts.

**Positive:** Section-level components are well-structured. The dashboard is decomposed into `EditorialQueueSection`, `ReviewQueueSection`, `MyArticlesSection`, `CategoriesSection` — each a focused sub-component. The admin dashboard similarly uses `GlobalUsersSection` and `NewspaperUsersSection`.

**Recommendations:**

1. Decompose `ArticleEditorPage.tsx` into sub-components and hooks: extract `useArticleEditor(articleId)` for data+save logic, `useImageGallery(articleId)` for image management, and render sub-components `ArticleMetadataPanel`, `ArticleCoverSection`.
2. Extract `useArticleComments(articleId)` and `useArticleLikes(articleId)` from `ArticlePage.tsx` using `useMutation` for the write operations.
3. Migrate raw `fetch` calls in event handlers to `useMutation` hooks — this automatically surfaces loading/error state without manual `useState` tracking.
4. Explore React Router v7 route loaders for the article page and category page to load data in parallel with the render, eliminating the initial loading spinner.
