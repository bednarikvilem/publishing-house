# Project Review: pb138

**Date:** 2026-06-07

---

## Project Orientation

The project is a Turborepo monorepo with two apps: `apps/server` (Elysia 1.4 on Bun with Drizzle ORM + PostgreSQL 17, JWT via `@elysiajs/jwt` and `Bun.password` for argon2) and `apps/web` (React 19 + React Router v7 + TailwindCSS v4 + shadcn/ui). Supporting infrastructure includes Redis (session/cache), MinIO (S3-compatible image storage), and Nodemailer (Mailtrap sandbox). The backend uses a service-layer architecture under `apps/server/src/services/` with route files in `apps/server/src/routes/`. Row-Level Security (RLS) is enforced at the PostgreSQL level via GUC session variables, providing defence-in-depth for multi-tenant data isolation. A custom structured logger (`apps/server/src/utils/logger.ts`) emits NDJSON and replaces all `console.log` in production server code. The test suite covers schema validation (TypeBox), RLS policies, utility functions, and E2E flows (Playwright).

`shadcn` is listed in `apps/web/package.json` and the generated components are in `apps/web/src/components/ui/`. `Button`, `Input`, `Select`, `Textarea`, `Badge`, and `Table` are all library-based. The handful of raw HTML elements found are legitimate:

- `apps/web/src/pages/profile/ProfileInfoCard.tsx:158` — `<input type="file">` for profile picture upload.

None of these are bypasses; they are justified native-element uses where the library provides no equivalent.

**Recommendations:**

**Recommendations:**

1. No immediate action required. Maintain the convention that arbitrary `[#hex]` and `[Npx]` values in application code are prohibited; all values must map to tokens defined in `globals.css`.

### 3. Loading Data

**Status:** ⚠️ Concerns — TanStack Query installed and used in some places, bypassed with raw `fetch()` in others

TanStack Query is correctly set up (`apps/web/src/lib/queryClient.ts`, `<QueryClientProvider>` in `apps/web/src/frontend.tsx`) and is used well in:
- `apps/web/src/pages/dashboard/EditorialQueueSection.tsx` — `useQuery` + `useMutation` with proper invalidation
- `apps/web/src/hooks/useNewspaper.ts`, `apps/web/src/hooks/useCategory.ts`
- `apps/web/src/components/Navbar.tsx`

However, the majority of pages fetch with raw `fetch().then()` chains:
- `apps/web/src/pages/AdminDashboardPage.tsx:19-31` — two direct `fetch` chains in `useEffect`
- `apps/web/src/pages/CategoryPage.tsx:47-55` — direct fetch in `useEffect`
- `apps/web/src/pages/SearchResultsPage.tsx:40-48` — direct fetch in `useEffect`
- `apps/web/src/pages/AuthorPage.tsx:49-55` — direct fetch in `useEffect`
- `apps/web/src/pages/DashboardPage.tsx:38-41` — direct fetch for user roles
- `apps/web/src/components/Sidebar.tsx:244-247` — direct fetch for current user
- `apps/web/src/components/StatisticsSection.tsx:38-47` — direct fetch for stats
- `apps/web/src/pages/dashboard/ReviewQueueSection.tsx`, `MyArticlesSection.tsx` — manual fetch in `useCallback`

This pattern means no caching, no background refetching, no loading/error state standardisation, and no deduplication. The `Sidebar.tsx` example is particularly concerning: it fetches on every mount with no caching.

Query keys, where used, are stable arrays: `["newspaper", name]`, `["category", id, slug]` — good pattern.

**Recommendations:**

1. Migrate all direct `fetch()` calls in component files to `useQuery` hooks. Each fetch in a `useEffect` can be replaced with a `useQuery` call with minimal effort.
2. Move Sidebar's user-fetching to a shared `useCurrentUser` hook backed by `useQuery` to cache the result globally.
3. The `ReviewQueueSection` and `MyArticlesSection` patterns using `useCallback` + manual `setLoading`/`setError` are exactly what `useQuery` replaces — migrate these.

### 5. REST API Design

**Status:** ⚠️ Concerns — Resource-oriented routes with good verb usage, but workflow actions as POST sub-resources and a missing 204 on some deletes

Routes are resource-oriented under `/api/newspapers/:id/articles`, `/api/newspapers/:id/categories`, etc. HTTP verbs are used correctly: `POST` for create, `PATCH` for partial update, `DELETE` for delete. Status codes are mostly correct:
- `201` on article create (`apps/server/src/routes/articles.ts`)
- `204` on article delete and image delete
- `401`/`403` from middleware

Workflow actions (`/submit`, `/approve`, `/review`, `/publish`, `/assign-editor`) are expressed as POST sub-resources, which is a legitimate REST pattern for state transitions.

**Concerns:**

- `POST /api/newspapers/:id/articles/:id/views` — `apps/server/src/routes/views_route.ts:22` returns what appears to be `200` with body rather than `201`.
- `DELETE /api/newspapers/:id/comments/:id` — need to confirm it returns `204`. The pattern exists for articles but comments were not verified.
- The `PATCH /api/newspapers/:id/articles/:id` handler (`updateArticleBody` schema) needs verification that it accepts partial fields only (correct PATCH semantics), not the full resource.

Request validation uses TypeBox (`@sinclair/typebox`) through Elysia's native schema validation (`apps/server/src/schemas/articles.ts`), which is the correct approach for this stack.

**Recommendations:**

1. Verify `views_route.ts` returns `201` (created) not `200` on the POST.
2. Audit all DELETE handlers to confirm they return `204` with no body.
3. Confirm `updateArticleBody` in `apps/server/src/schemas/articles.ts` marks all fields `Optional` (partial update pattern).

### 6. Database

**Status:** ✅ Good — well-designed schema, migrations present, ORM used throughout

The schema in `apps/server/src/db/schema.ts` is well-structured: normalised relational tables with UUID PKs, appropriate foreign keys with `CASCADE` and `SET NULL` delete behaviours, composite primary keys on join tables (`likes`, `userRoles`), and unique constraints (`email_newspaper_idx`, `global_roles_role_unique`). No `bytea`/`blob` columns — images are stored in MinIO with URLs in the DB.

Migrations are versioned: 6 SQL files in `apps/server/drizzle/` (`0001` through `0006`) covering schema additions, RLS, and index fixes. One TypeScript migration (`apps/server/src/db/migrations/addGlobalEmailUniqueIndex.ts`) exists alongside the SQL files — this is a minor inconsistency (mixing migration formats) but not blocking.

DB queries use Drizzle ORM throughout the service layer. The `withRls()` wrapper (`apps/server/src/db/rls.ts`) sets PostgreSQL session GUCs before every query, enforcing RLS per-request.

One `db.select().from(newspapers)` call appears directly in `apps/server/src/server.ts:79` (the `/api` health endpoint) — this is a minor layer-violation.

**Recommendations:**

1. Move the `db.select()` in `server.ts:79` into a service or query function, even for a health endpoint.
2. Consolidate the TypeScript migration (`addGlobalEmailUniqueIndex.ts`) into the SQL migration format for consistency.

### 7. Backend Design Patterns

**Status:** ⚠️ Concerns — service layer exists but is oversized; no repository layer

The project has a clear two-layer structure: `apps/server/src/routes/` (thin Elysia route handlers) and `apps/server/src/services/` (business logic). Route handlers delegate to service functions correctly — no DB calls appear directly in route files.

However, `apps/server/src/services/articles.ts` is **1057 lines** — well beyond the ~200–300 line guideline. It handles article CRUD, submission workflow, image upload, review, approval, scheduling, publication, and search. This is a god-service that mixes multiple distinct concerns.

No repository layer exists: services call Drizzle directly. For this project size this is acceptable, but the `articles.ts` service would benefit from extraction.

**Recommendations:**

1. Split `apps/server/src/services/articles.ts` into at least three files: `articleQueries.ts` (reads/search/listing), `articleWorkflow.ts` (submit/review/approve/publish state machine), and `articleImages.ts` (upload/delete).
2. Consider a repository pattern for complex Drizzle queries to keep service functions focused on business rules.

### 8. Auth

**Status:** ✅ Good — JWT-based auth with Elysia middleware, authorization enforced via RLS + service checks

Authentication uses `@elysiajs/jwt` (not manual `jsonwebtoken`). `Bun.password` handles argon2 hashing — no raw `bcrypt` wiring. The `authMiddleware` (`apps/server/src/middleware/auth.ts`) decodes the JWT, checks the JTI blocklist in Redis (logout support), loads user + roles from DB, and exposes a `withDb()` closure that wraps every query in RLS session context.

Authorization is enforced at two levels:
1. **Route level** — `requireAuth` and `requireRole(role)` middleware Elysia guards.
2. **Database level** — PostgreSQL RLS policies filter rows based on `app.user_id`, `app.newspaper_id`, `app.roles` GUCs set by `withRls()`.

Service-level authorization checks also exist (e.g., `apps/server/src/services/categories.ts:81` logs `"Category create failed: forbidden"` before throwing). No 403 bypasses were found.

**Recommendations:**

1. No action required. The layered auth approach (middleware + RLS + service checks) is a strong security posture.

### 11. Error Handling

**Status:** ⚠️ Concerns — global handler excellent, but frontend error states are inconsistent

**Backend:** Global `onError` handler in `apps/server/src/server.ts:94` catches all `HttpError` instances and returns structured JSON with the correct status code, and logs unhandled errors with full context. **Frontend concerns:**

- `apps/web/src/components/Sidebar.tsx:244-247` — `.then(setUser).catch(...)` — no catch block shown in the grep output; if the fetch fails, the sidebar may silently show nothing.

**Recommendations:**

1. Standardise frontend error handling: where `useQuery` is adopted (per recommendations in Loading Data), error states come for free via `isError`.
2. For the sidebar user fetch, ensure a visible fallback or error state if the fetch fails.

### 13. Forms

**Status:** ❌ Issues — no form library; all forms are hand-rolled with `useState` + manual validation

No form library (React Hook Form, TanStack Form, Formik) is in `apps/web/package.json`. No validation library (Zod, Yup, Valibot) is wired to forms. All forms are hand-rolled:

- `apps/web/src/pages/SignUpPage.tsx` — 10 `useState` calls, manual `handleSubmit`, manual field error state via `setFieldErrors({})`. Server validation errors are mapped manually from API responses.
- `apps/web/src/pages/profile/ProfileInfoCard.tsx` — 12 `useState` calls including form fields, loading, errors.
- `apps/web/src/pages/profile/PasswordCard.tsx` — `useState` for old password, new password, confirm password, plus manual `setError("Passwords do not match")` and `setError("Password must be at least 8 characters")`.
- `apps/web/src/pages/LoginPage.tsx`, `GlobalLoginPage.tsx` — manual fetch + `useState` for error.

This is the form-as-useState anti-pattern at scale. The codebase has multiple duplicated patterns: every form re-implements `setLoading(true)`, `try { await fetch(...) } catch { setError("Something went wrong") } finally { setLoading(false) }`.

`apps/web/src/components/FormField.tsx` exists as a thin wrapper around `<Input>` with label and error display — this is good, but without a form library driving it, each form still manually manages all state.

**Recommendations:**

1. Adopt React Hook Form + `@hookform/resolvers` + Zod for all forms. This eliminates the manual `useState` chains and provides consistent validation, error display, and loading states.
2. Define Zod schemas for each form (registration, login, password change, profile update) — these schemas can also be shared with the backend TypeBox schemas conceptually.
3. Migrate `SignUpPage.tsx` first as a template: it has the most complexity (field errors + server errors + loading) and demonstrates the full pattern.
