# Project Review: pb138

**Date:** 2026-06-05

---

## Project Orientation

This is a full-stack web application for a multi-newspaper publication house, implemented as a Turborepo monorepo. The frontend is built with React 19 and React Router, styled with TailwindCSS, and communicates with the backend via an Elysia Eden Treaty client (though most components still use raw `fetch`). The backend is an Elysia/Bun server with Drizzle ORM talking to PostgreSQL, Redis for session token blocklisting, and MinIO for file storage. Authentication is hand-rolled using JWT (Elysia's JWT plugin) with Bun.password argon2 hashing. Row-level security (RLS) policies are enforced at the database level for multi-tenant isolation.

Testing is split across a small unit test suite in the server workspace and 15 Playwright E2E specs covering the main user flows. The project ships via Docker Compose with separate containers for the server, web, PostgreSQL, Redis, and MinIO. There is no CI/CD pipeline. Key tooling includes Drizzle for schema management (push-based, with sequential SQL migration files), bun for all package management and script execution, and Turborepo for task orchestration.

## Detailed Review

### 1. Component Library
**Status:** ⚠️ Concerns — UI primitives exist but not consistently adopted across the codebase

The project has a `components/ui/` directory with `button.tsx`, `card.tsx`, `input.tsx`, `label.tsx`, `select.tsx`, and `textarea.tsx`, backed by `@base-ui/react`. However, multiple pages bypass these primitives in favour of raw HTML elements:

- `apps/web/src/pages/ArticleEditorPage.tsx` (lines 164, 491, 505): raw `<input>` and `<textarea>`
- `apps/web/src/pages/LoginPage.tsx` (line 86): raw `<input type="password">`
- `apps/web/src/components/Navbar.tsx`: raw `<input>` elements
- `apps/web/src/pages/profile/ProfileInfoCard.tsx` (line 200): raw `<input type="email">` for read-only display
- `apps/web/src/components/RichTextEditor.tsx`: raw `<input type="file">`
- Several pages use raw `<button>` elements with inline Tailwind instead of the Button component (e.g., `DecisionForm`, `PortalLayout`)

A `FormField` wrapper exists in `apps/web/src/components/FormField.tsx` but is not used everywhere.

**Recommendations:**
1. Create an Input variant for file uploads and password fields using the existing Input primitive.
2. Audit all pages and replace raw `<button>` elements with the Button UI component.
3. Use `FormField` for all text inputs; create variants for read-only and file upload cases.
4. Add a `SelectField` wrapper to match the `FormField` API.

### 3. Loading Data
**Status:** ❌ Issues — Heavy reliance on raw `fetch()` instead of the installed treaty client; no request caching layer

The Eden Treaty client is defined in `apps/web/src/lib/api.ts` (lines 12–14):
```ts
export const client = treaty<App>(API_BASE_URL, { headers: () => authHeaders() });
```

However, **raw `fetch()` calls dominate** (65+ `useEffect` + fetch patterns across the codebase):
- `apps/web/src/pages/ArticleEditorPage.tsx`: 3 fetch calls (lines 241, 249, 265)
- `apps/web/src/pages/ArticlePage.tsx`: fetch call (line 108)
- `apps/web/src/components/Navbar.tsx`: 3 fetch calls (lines 70, 87, 94)
- `apps/web/src/pages/DirectorDashboardPage.tsx`: 2 fetch calls (lines 24, 35)
- Helper functions in `apps/web/src/lib/api.ts` themselves use raw `fetch` (lines 19, 31, 49, 62)

No TanStack Query, SWR, or equivalent caching layer is installed. Every component manually manages `loading`/`error` state, leading to duplication and no request deduplication.

**Recommendations:**
1. Adopt `@tanstack/react-query` to replace manual fetch + useState patterns.
2. Migrate all `fetch()` calls to use the treaty client for type safety.
3. Create custom hooks (`useFetchArticles`, `useFetchUser`, etc.) that wrap Query.
4. Implement automatic cache invalidation on mutations.

### 5. REST API Design
**Status:** ⚠️ Concerns — HTTP verbs mostly correct, but one PUT/PATCH semantics violation and in-memory filtering on two endpoints

**PUT/PATCH semantics issue:**
- `PUT /api/users/me` (`apps/server/src/routes/users.ts` line 14) uses a body schema with all-optional fields (`username`, `full_name`, `password`, `bio`). Optional fields signal partial update (PATCH semantics), not full replacement (PUT semantics).

**In-memory filtering (performance risk):**
- `searchArticles()` (`apps/server/src/services/articles.ts` lines 60–80): loads all articles from DB, then filters in-memory.
- `listCommentsForModeration()` (`apps/server/src/services/comments.ts` lines 144–156): loads all comments with relations, then filters by `newspaperId` and `article_id` in JS with a self-acknowledged TODO comment.

**What's good:**
- CORS restricted to `FRONTEND_URL` env var (not wildcard).
- HTTP status codes correct: 201 for creates, 204 for deletes, proper 400/401/403/404 usage.
- All URLs are resource-oriented and plural.

**Recommendations:**
1. Change `PUT /api/users/me` to `PATCH /api/users/me`.
2. Push filtering logic for `searchArticles` and `listCommentsForModeration` into Drizzle `where` clauses with database-side pagination.

### 6. Database
**Status:** ✅ Good — UUIDs with `defaultRandom()`, proper foreign keys with cascade rules, composite PKs on join tables, RLS enforced, parameterized queries throughout

- All tables use `uuid("id").primaryKey().defaultRandom()`.
- Foreign keys have appropriate `onDelete` rules (`cascade` for user data, `set null` for optional anonymous views).
- Join tables use composite PKs: `userRoles` on `[userId, newspaperId, role]`, `likes` on `[userId, articleId]`.
- Images and profile pictures stored as URL strings, not blobs.
- Sequential SQL migration files (`0001`–`0006`) with a proper Drizzle journal.
- `apps/server/src/db/rls.ts` uses parameterized `sql` template tags (e.g., `sql\`SELECT set_config('app.user_id', ${session.userId ?? ""}, true)\``), no string concatenation.

**Recommendations:**
None — database design is solid.

### 8. Auth
**Status:** ✅ Good — Argon2 hashing, proper JWT expiry, token blocklist with Redis, RLS enforcement, audit logging

- Password hashing via `Bun.password.hash()` / `Bun.password.verify()` (argon2) — cryptographically strong.
- JWT expiration: session = 2h, email verification = 1d, password reset = 1h (`apps/server/src/utils/jwt.ts`).
- JTI (JWT ID) included for token blocklisting; checked against Redis on every authenticated request (`apps/server/src/middleware/auth.ts` line 26).
- `requireAuth` and `requireRole` middleware applied to all protected routes.
- Login blocked if `email_verified = false` (`apps/server/src/services/auth.ts` lines 133–137).
- All auth events logged with structured logger: `USER_REGISTER`, `USER_LOGIN`, `EMAIL_VERIFIED`, `PASSWORD_RESET`.
- Comprehensive RLS policies in `drizzle/0002_enable_rls.sql` with helper functions `has_newspaper_role()`, `is_editorial_of()`, `is_admin()`, and `can_see_article()`.

**Recommendations:**
None — authentication is well-designed and secure.

**Recommendations:**

2. Move test credentials to `.env.test` or a fixture config, or at minimum remove credential logging from seed scripts.

## Overall Summary

The project demonstrates solid foundational decisions: the database schema is well-designed with UUIDs, proper cascades, composite PKs on join tables, and comprehensive RLS policies enforced at the DB level. Authentication is strong — argon2 hashing, JWT with Redis-backed token blocklisting, and structured audit logging. The E2E test suite covers the main user journeys including the full article publication workflow and role management.

The most significant weaknesses are in the frontend data layer and structure. Raw `fetch()` calls dominate despite an installed Eden Treaty client, with no caching or deduplication layer — this should be the top priority fix before submission. Several large page components (ArticleEditorPage at 561 lines, ArticlePage at 441 lines) mix too many concerns and define inline sub-components with excessive prop drilling; extracting custom hooks and splitting god components would significantly improve maintainability. The absence of CI/CD means code quality relies entirely on manual review, and the web Docker container running a hot-reload dev server in production is a deployment correctness issue that should be fixed.

Before submission, prioritise: (1) migrate data fetching to TanStack Query + treaty client, (2) fix the web Dockerfile to build and serve a production bundle, (3) add a CI pipeline for test and lint on PR, and (4) replace silent `.catch(() => {})` handlers with visible error states.
