# Project Review: pb138

**Date:** 2026-06-04

---

## Project Orientation

This is a full-stack web platform for a publication house managing multiple newspapers. The stack is a Turborepo monorepo with a React 19 + React Router + TailwindCSS frontend (`apps/web`) and an Elysia + Bun backend (`apps/server`) backed by PostgreSQL via Drizzle ORM. Image storage uses MinIO, email is handled by Nodemailer, and Redis is used for JWT blocklisting. Authentication is hand-rolled with JWT (sign/verify via `jose`), Argon2 password hashing via `Bun.password`, and Row-Level Security policies in PostgreSQL enforced through Drizzle's `sql` template tags.

The project includes E2E tests with Playwright (`tests/e2e/`) covering full multi-user article workflows, plus unit/schema tests under `apps/server/tests/`. The user role model is multi-tiered (Visitor, Registered User, Author, Editor, Manager, Director, System Administrator) with per-newspaper roles. Deployment is Docker-based via `docker-compose.yml`.

## Detailed Review

### 1. Component Library
**Status:** ⚠️ Concerns — UI library underutilized; mostly raw HTML elements used instead of primitives

The project has a well-structured UI component library in `apps/web/src/components/ui/`:
- `button.tsx` — wrapper around `@base-ui/react/button`
- `input.tsx` — wrapper around `@base-ui/react/input`
- `textarea.tsx` — raw HTML textarea with Tailwind styling
- `select.tsx` — wrapper around `@base-ui/react/select`
- `card.tsx`, `label.tsx` — basic wrappers

However, raw HTML elements are heavily preferred over the library throughout:
- **65 raw `<input>`, `<button>`, `<textarea>` elements** used directly in page files vs library components
- Only **31 uses of the UI components** (Button, Input, Textarea, Select, Label, Card) across the entire codebase
- `apps/web/src/pages/ArticleEditorPage.tsx` (lines 491–512): Raw `<input>` and `<textarea>` with inline className instead of Input/Textarea components
- `apps/web/src/pages/dashboard/EditorialQueueSection.tsx` (lines 239–251): Raw `<select>` instead of Select component
- `apps/web/src/pages/profile/ProfileInfoCard.tsx` (lines 200–206): Raw `<input>` with inline styling
- The `@base-ui-components/react` dependency (v1.0.0-rc.0) is installed but never imported or used anywhere

**Recommendations:**
1. Migrate all raw `<input>` elements to the Input component from `components/ui/input`
2. Replace raw `<button>` elements with Button component from `components/ui/button`
3. Replace raw `<textarea>` with Textarea component and raw `<select>` with Select component
4. Remove unused `@base-ui-components/react` if it is not needed

### 5. REST API Design
**Status:** ⚠️ Concerns — PUT endpoint uses optional fields (PATCH semantics violation), CORS is wildcarded, and status codes are mostly correct but inconsistent

**PUT with Optional Fields (PATCH Semantics Violation):**
- `apps/server/src/schemas/articles.ts` (lines 65–71):
  ```typescript
  export const updateArticleBody = t.Object({
    title: t.Optional(t.String({ minLength: 1, maxLength: 255 })),
    perex: t.Optional(t.String({ minLength: 1, maxLength: 1000 })),
    content: t.Optional(t.String({ minLength: 1, maxLength: 200_000 })),
    category_id: t.Optional(t.Union([Uuid, t.Null()])),
    keywords: Keywords,
  });
  ```
- Used in `apps/server/src/routes/articles.ts` (line 82–88) with PUT HTTP verb. PUT should replace the entire resource with required fields; optional fields indicate PATCH semantics.

**Wildcard CORS:**
- `apps/server/src/server.ts:30`: `.use(cors())` called with no options, enabling wildcard CORS

**HTTP Status Codes:**
- 201 for POST creation: articles.ts, categories.ts, comments.ts, likes.ts, subscriptions.ts ✓
- 204 for DELETE: articles.ts, comments.ts, categories.ts ✓
- `views_route.ts:28` uses conditional `200 : 201` for the same POST endpoint (inconsistent)

**URL Patterns:**
- Generally resource-oriented: `/api/newspapers/:id/articles`, `/api/newspapers/:id/categories` ✓
- Action endpoints (`/articles/:id/submit`, `/articles/:id/publish`, `/articles/:id/assign-editor`) are acceptable for complex state transitions

**Recommendations:**
1. Change `updateArticleBody` to require all fields OR change the PUT route to PATCH
2. Configure CORS with explicit allowed origins: `.use(cors({ origin: process.env.CORS_ORIGIN }))`
3. Standardize view recording endpoint to return 201 only on creation, not on updates

**Recommendations:**
1. Add `{ onDelete: "cascade" }` to `users.newspaperId`, `userRoles.userId`, `userRoles.newspaperId`, `articles.authorId`, and `articles.newspaperId`

### 12. Security
**Status:** ❌ Issues — CORS misconfigured (wildcard), plaintext passwords logged, no security headers

**CORS wildcard:**
- `apps/server/src/server.ts:30`: `.use(cors())` with no options sets `Access-Control-Allow-Origin: *`, allowing any origin to call the API

**No security headers:**
- No middleware sets `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, or similar headers
- Elysia has no built-in Helmet equivalent

**SQL injection risk:**
- Not present — all DB access goes through Drizzle ORM or parameterized `sql` template tags ✓

**Error response sanitization:**
- `apps/server/src/errors/index.ts` and `server.ts:85` allow arbitrary `ErrorDetails` in HTTP responses with no guardrail preventing sensitive data leakage in error bodies

**Recommendations:**
1. Configure CORS explicitly: `.use(cors({ origin: process.env.CORS_ORIGIN || "http://localhost:5173" }))`
2. Remove plaintext credential logs from seed scripts
3. Add security headers middleware (custom or a community plugin) setting at minimum `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`
4. Audit all `ErrorDetails` returned from service layer to ensure no internal state leaks

## Overall Summary

The project demonstrates strong fundamentals in authentication (Argon2, JWT blocklist, comprehensive RLS policies), database design (UUID PKs, composite PKs for join tables, sequential migrations), and testing (E2E Playwright coverage of full article workflows with zero skipped tests). The main weaknesses are concentrated in the frontend and backend service layer: the frontend has three oversized god components (ArticleEditorPage at 561 lines, ArticlePage at 441 lines), relies on 68 raw fetch calls instead of the treaty client or a query library, and uses manual form validation scattered across 18+ useState hooks per component instead of a form library. On the backend, `articles.ts` at 1057 lines and `admin.ts` at 824 lines each violate single responsibility. Two critical security issues should be addressed before submission: CORS is misconfigured with a wildcard allowing any origin, and seed scripts log plaintext user passwords which can leak into CI pipelines. Priority fixes are: (1) restrict CORS to allowed origins, (2) remove plaintext credential logs, (3) add a CI/CD pipeline, (4) split the monolithic service files, and (5) introduce a form library and custom hooks to decompose god components.
